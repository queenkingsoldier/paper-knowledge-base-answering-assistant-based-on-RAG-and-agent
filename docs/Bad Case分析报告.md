## 0. 本报告的口径

本报告**不是**「设想中可能出什么问题」的清单，而是**开发过程中真实观察到、定位到根因、并已修复或已定性**的 6 个缺陷。

每一个都给出：现象（含原始输出）→ 复现方式 → 根因 → 修复 → **修复前后的实测数据**。

**没有观测到的类别也如实标注**（见 §4），不编造案例。

## 1. Agent 决策错误

### BC-01 · 规则路由已实现却从未被调用，纯算术问题照走检索

**现象**：Agent 工具调用准确率 **0.9091（20/22）**，两条工具类问题被误判：

| 问题 | 期望工具 | 实际工具 |
|---|---|---|
| `3.14 乘以 2.56 等于多少？` | `calculator` | `kb_search` |
| `现在是几点？` | `current_time` | `kb_search` |

**复现**：

```bash
python scripts/eval_agent.py --qa eval/qa_set_demo.jsonl
# 首次运行：工具调用准确率 : 0.9091
```

**根因**：`agent/router.py` 实现了完整的规则路由（8 条单测全绿），但 `agent/react.py` 的 `ReActAgent.run()` **从未调用它**。前端 `streamlit_app.answer_once()` 里用 `classify()` 只是为了判断空知识库，路由结果被丢掉了。

结果：路由模块成了「写了但没接线」的孤岛——单元测试全通过，因为它自己工作正常；而**集成层没有任何测试断言「路由结果真的影响到了 Agent 行为」**。

**修复**：在 `ReActAgent.run()` 入口接入 `_direct_route()`：命中 `direct_tool` 时直接执行工具并返回 `AgentResult(route="direct_tool")`，跳过整个 ReAct 循环。放在 `run()` 里而不是前端，是为了让**所有入口**（CLI、评测脚本、前端）都受益。

**修复前后对比**：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 工具调用准确率 | 0.9091 | **1.0000** | +0.0909 |
| Prompt token 总量 | 44,055 | **40,003** | **−9.2%** |
| 平均推理轮次 | 2.000 | 1.909 | −0.091 |

第二行是意外收益：短路掉两次无谓的 ReAct 循环，token 直接降了 9.2%——正对应构建书 §5.3.3「减少无效推理轮次」。

**教训**：**单元测试全绿 ≠ 功能接通**。模块级测试只能证明模块自身正确，证明不了它被调用。这类缺陷必须靠集成层断言（现在 `tests/test_integration.py` 会检查 Agent 的 Observation 里确实带回了知识库来源）。

### BC-02 · 中文口语运算符不被识别

**现象**：修完 BC-01 后准确率升到 0.9545，仍有一条失败：

| 问题 | 期望 | 实际 |
|---|---|---|
| `3.14 乘以 2.56 等于多少？` | `calculator` | `kb_search` |

**根因**：路由的算式抽取正则 `_EXPR_FRAGMENT_RE = [-+*/().\d\s]+` 只认符号。中文用户写「乘以」而不是「*」，`"3.14 乘以 2.56"` 被切成 `"3.14 "` 和 `" 2.56 "` 两个片段，**没有一个片段同时含运算符和两个数字**，因此判定失败。

**这不是边缘情况**：构建书 §5.3.1 举的路由示例原文就是「3.14乘以2.56」。规格里明确要支持的主路径，实现时漏了。

**修复**：抽算式前先把中文运算符词归一化成符号：

```python
_CN_OPERATORS = (("乘以", "*"), ("乘上", "*"), ("乘", "*"),   # 长词必须在前，
                 ("除以", "/"), ("除", "/"),                 # 否则「乘以」先被「乘」拆掉
                 ("加上", "+"), ("加", "+"),
                 ("减去", "-"), ("减", "-"))
```

**误判防护**：归一化会把「加速度」里的「加」也替换掉。但算式判定还要求片段里**至少两个数字**，`"+ 速度"` 只有一个数字，会被拒绝。实测边界：

| 输入 | 判定 | 是否正确 |
|---|---|---|
| `3.14 乘以 2.56 等于多少？` | `calculator` | ✅ |
| `3.14 * 2.56` | `calculator` | ✅ |
| `3.14`（纯数字） | `agent` | ✅ 不误判 |
| `论文1和论文2的区别`（两数字无运算符） | `agent` | ✅ 不误判 |
| `加速度对训练的影响` | `agent` | ✅ 不误判 |

**修复后**：准确率 **0.9545 → 1.0000（22/22）**。

**教训**：规格里举的例子就是必须支持的输入。写实现时把规格的示例当测试用例，能直接拦住这类缺陷。

## 2. 检索失败 / 检索架构

### BC-03 · 重排序在片段级口径下反而使检索变差

**现象**：片段级（精确到段）评测中，重排序**降低**了检索质量：

| 档位 | Hit@3 | MRR | Recall@5 |
|---|---|---|---|
| `hybrid`（RRF 融合） | **1.00** | **0.8167** | **0.965** |
| `hybrid_rerank`（+重排序） | 0.95 | 0.7933 | 0.950 |

但在文档级口径下重排序是**提升**的：

| 档位 | MRR |
|---|---|
| `hybrid` | 0.9167 |
| `hybrid_rerank` | **0.9667** |

**根因**：重排序用的是 `MockRerank`——**按查询与文档的词元重合度打分**，它是一个单路词汇匹配器，**信息量低于 RRF**。RRF 融合了向量与 BM25 两路信号；用一个信息量更少的打分器去重排一个信息量更多的排序，必然丢失信息。在需要精确到段的片段级口径上，这种损失直接暴露为 Hit@3 与 MRR 下降。

**定性**：这**不是架构缺陷，是 Mock 打分器的能力缺陷**。真实 `bge-reranker-v2-m3` 是交叉编码器，对 (query, passage) 联合编码，信息量严格多于任何单路检索分数。

**处理**：未改代码。理由：

1. 降级与容错链路是正确的（provider 抛异常会退回上游顺序，`degraded` 如实上报）；
2. 换成真实 API 后大概率自然消失，此时改代码是在为假数据打补丁；
3. **这个「负面结论」本身就是有价值的发现**——它证明了为什么重排序必须用交叉编码器，而不能拿一个简单相似度函数凑数。

**待办**：填充真实 `SILICONFLOW_API_KEY` 后重跑，验证 `hybrid_rerank` 在**两个口径下都**优于 `hybrid`。

### BC-04 · chunk_size=512 的「满分」是评测假象，不是检索质量

**现象**：分块消融实验中，`recursive/512` 的 `hybrid` 档取得 MRR **1.0000**，看起来远超 `recursive/256`（0.9250）。

**根因**：`chunk_size=512` 时 4 篇文档只切出 **4 个 chunk**（一段一块）。top-5 必然覆盖全部 4 块，**Hit@5 = 1.00 在数学上必然成立**，与检索质量无关。它甚至无法产生 5 条候选供 RRF 融合。

**处理**：这不是代码缺陷，是**评测方法缺陷**。已在《分块策略对比实验报告》§4.3 明确标注该结论不可用，并给出正确做法（语料扩充到 10-20 篇后重跑）。

**教训**：指标饱和时，配置之间的比较毫无意义。评测前必须先检查「指标是否有区分度」。

## 3. 集成缺陷（工程实现错误）

这三条不对应作业的四类 Bad Case，但都是真实观察到、影响可用的缺陷，一并记录。

### BC-05 · `semantic` 分块策略在 CLI 与 UI 上完全不可用

**现象**：分块消融跑到 `--strategy semantic` 时脚本直接崩：

```
TypeError: SemanticChunker.__init__() got an unexpected keyword argument 'overlap'
```

**根因**：`get_chunker(strategy, **kw)` 把所有 kwargs 不加区分地转发给目标类：

```python
if name == "semantic":
    return SemanticChunker(**kw)     # ← overlap 被一起传进去了
```

而 `SemanticChunker(chunk_size, threshold, embed_fn)` 没有 `overlap` 参数——这是**有意的设计**（语义块之间靠向量断点衔接，再叠文本重叠只会重复占用上下文预算）。

**为什么单测没拦住**：计划书的 `test_chunker_factory_returns_expected_types` 调用的是 `get_chunker("semantic")`，**不带任何 kwargs**。而 CLI 和 `streamlit_app` 都固定传 `chunk_size=..., overlap=...`。测试覆盖了工厂的正常路径，没覆盖真实调用签名。

**影响面**：CLI 与前端配置 `CHUNK_STRATEGY=semantic` 时 100% 崩溃；只有不传参数的测试路径是好的。

**修复**：工厂只转发目标类真正接受的参数：

```python
accepted = inspect.signature(cls).parameters
forwarded = {k: v for k, v in kw.items() if k in accepted}
```

**修复验证**：三种策略在 CLI 下均正常，`semantic/256` 产出 8 个 chunk，退出码 0。

**教训**：工厂函数用 `**kw` 透传时，必须验证每个目标类的签名。只测「不传参数」的路径会给假信心。

### BC-06 · `--rebuild` 只清向量库不清 BM25，导致残留旧 chunk

**现象**：先用 `chunk_size=512` 建索引（4 chunk），再 `--rebuild --chunk-size 200`，结果索引里出现 **14** 个 chunk，而正确值应为 10。

**根因**：`build_index.py` 的 `--rebuild` 只调 `vectorstore.delete_document()`，**没有清 BM25**。新旧 chunk 的 `chunk_id` 形如 `{doc_id}::{page_no}::{seq}`：旧配置每篇只有 `seq=0`，新配置有 `seq=0..3`。于是 4 个 `seq=0` 的 ID 发生碰撞被去重，剩下 6 个新 ID 被追加 → `4 + 6 = 10`……再叠加此前多轮实验的累积，最终得到 14。

**后果**：检索会召回到**已经不该存在**的片段，且回答里的引用页码可能与当前分块方案不一致。这是很难察觉的静默数据污染。

**修复**：

1. `BM25Index` 增加 `clear()`（`build([])` 的语义化封装）；
2. `--rebuild` 同时清空两套索引；
3. 日志同时打印两边清掉的 chunk 数，便于核对。

**修复验证**：连续用 200 → 300 两种 `chunk_size` 重建，两边计数始终一致（10/10、8/8），无残留。

**教训**：一个逻辑索引只要存在**多个物理存储**，任何「重建/删除」操作都必须覆盖全部副本，否则就会出现两个库对不上的静默不一致。

### BC-07 · 工具依赖是模块级全局状态，导致跨测试文件污染

**现象**：`pytest tests/test_tools_kb.py` 单独跑 **7 passed**；`pytest tests/` 整套跑则 **2 failed**：

```
assert '未找到' in '知识库中还没有任何已入库文档。请先在「文档管理」上传 PDF。'
```

**根因**：工具依赖用模块级全局变量注入（`set_engine` / `set_vectorstore`）。`test_integration.py` 先运行并调用 `build_agent()`，把**它自己的** VectorStore 注入到了 `paper_meta` 模块；随后 `test_tools_kb.py` 运行，其 autouse fixture **只重新注入了 `kb_search`**，`paper_meta` 仍持有上一个测试文件留下的空库。

**为什么计划书有责任**：计划书里这个 fixture 只写了 `kb_mod.set_engine(engine)`——覆盖不全，是我写计划时的疏漏。

**修复**：fixture 改为走**生产注入路径** `agent._inject_dependencies(...)`，一次注入全部工具：

```python
@pytest.fixture(autouse=True)
def _inject(engine):
    from agent import _inject_dependencies
    _inject_dependencies(engine, engine.retriever, getattr(engine, "llm", None) or MockLLM())
```

好处有两层：测试隔离正确了，**且生产注入函数本身也被测到了**。

**修复验证**：单独跑 7 passed；两个文件的组合 13 passed；全量 **228 passed**。

**教训**：模块级全局状态一旦引入，测试之间就不再隔离。fixture 必须覆盖**全部**注入点，且最好复用生产代码路径而不是手写一份平行的注入逻辑——手写的那份一旦落后于生产就会失真。

## 4. 未观测到的类别（如实说明）

| 类别 | 状态 |

| **生成错误**（回答不准确/遗漏） | **未能有效评估**。Mock LLM 返回固定话术，答案质量无从判断。需真实 API 后由人工评分。 |
| **引用错误**（标注了错误的来源） | **未观测到错误案例**。引用由 `_extract_citations` 从 Observation 正则抽取并按序号重编号，且有 `validate_citations` 过滤越界编号。但 Mock 场景下 LLM 不产生真实引用行为，**真实模型下是否会出现「编造引用编号」需重新验证**。 |
| **检索失败**（未召回相关文档） | 见 BC-03 / BC-04，均为架构或评测方法问题，而非「某条查询召回失败」的具体案例。片段级 Hit@5 为 1.00，无失败案例可分析。 |

**这三类都需要真实 API 才能产出有意义的 Bad Case。** 当前不编造案例填充。

### 三条可迁移的教训

1. **单元测试全绿 ≠ 功能接通**。BC-01 与 BC-05 都是「模块自身测试通过、集成层完全没接线/签名不匹配」。必须有集成层断言。
2. **规格里的示例就是必须支持的测试用例**。BC-02 直接源于规格示例（「3.14乘以2.56」）没有被当成验收条件。
3. **多物理存储的删除操作必须覆盖全部副本**。BC-06 是典型的静默不一致，不报错、不崩溃，只会让检索结果悄悄变错。
