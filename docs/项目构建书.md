## 0. 文档说明

本构建书用于指导「智能科研助理」从零到一的完整构建。它回答三个问题：

1. **用什么做**——每一个技术组件的选型、理由和被否方案；

3. **怎么算做完**——可验证的验收条件与评测方法。

阅读顺序建议：第 2 章（选型）→ 第 3 章（架构）→ 第 5 章（模块）→ 第 7 章（评测）。

### 0.1 关键约束（来自需求确认）

| 约束项 | 决定 | 影响 |
|---|---|---|
| 部署形态 | **不做本地模型部署，全部走云端 API** | Embedding/Rerank 也必须走 API，不能落地 sentence-transformers |
| LLM 供应商 | **DeepSeek** | 无 embedding 接口，必须另配向量化供应商 |
| 向量化供应商 | **SiliconFlow** | bge-m3 + bge-reranker-v2-m3，注册即有免费额度 |
| 前端 | **Streamlit** | 与作业文档指定方案一致 |
| 实现范围 | **五大模块全部实现并可运行** | 含评测脚本与全套报告 |
| 框架策略 | **关键处手写，工程处用库** | 不引入 LangChain/LlamaIndex |

### 0.2 术语表

| 术语 | 含义 |
|---|---|
| Chunk | 文档切分后的最小检索单元，携带来源坐标（文档名/页码/序号） |
| Hybrid Retrieval | 向量检索与 BM25 关键词检索并行，再融合排序 |
| RRF | Reciprocal Rank Fusion，倒数排名融合，一种免调参的多路排序融合算法 |
| Rerank | 用交叉编码器（cross-encoder）对候选集做精细相关性打分重排 |
| ReAct | Reason + Act，让 LLM 交替产生推理与工具调用的范式 |
| Trace | 一次请求的完整推理轨迹（Thought → Action → Observation） |
| Degradation | 降级：主链路失败时退到可用的次优链路，而非直接报错 |

## 1. 项目目标与成功标准

### 1.1 一句话目标

构建一个可交互的 Web 问答系统：用户上传论文 PDF，系统用混合检索精确定位证据，由 Agent 自主决策调用工具，最终生成**带引用溯源、可展示推理轨迹**的答案。

### 1.2 成功标准（可验证）

| 编号 | 标准 | 验证方式 |
|---|---|---|
| S1 | 上传 PDF/DOCX/TXT/MD 后能成功入库并返回 chunk 数 | `scripts/build_index.py` 输出入库统计 |
| S2 | 同一问题在 `vector` / `hybrid` / `hybrid+rerank` 三档下的 Hit@5 可测量 | `scripts/eval_retrieval.py` 产出对比表 |
| S3 | `hybrid+rerank` 的 Hit@5 高于纯 `vector` | 同上，且差异可复现 |
| S4 | 生成答案中的 `[n]` 标记能映射回真实文档名+页码 | 前端点击引用展示来源片段 |
| S5 | Agent 能对计算类问题跳过检索直接调计算器 | 轨迹中无 `kb_search` 调用 |
| S6 | Agent 单次请求最多 6 轮推理后强制收敛，不无限循环 | `eval_agent.py` 统计轮次分布 |
| S7 | 无命中/API 失败时系统给出明确提示而非崩溃 | 边缘场景用例 |
| S8 | 前端三栏（文档管理 / 对话 / 轨迹）均可交互 | 人工走查 |
| S9 | 全链路在无真实 API key 时可用 mock 模式跑通 | `scripts/smoke_test.py` 退出码 0 |

### 1.3 明确不做（YAGNI）

以下内容被有意排除，避免范围蔓延：

- **不做多用户鉴权与权限体系**：单机单用户使用，会话隔离仅用 session_id 区分。
- **不做 PDF 版面还原（OCR、公式 LaTeX 化）**：超出课程范围，PyMuPDF 的文本抽取已满足检索需求。
- **不做本地模型部署**：已由用户明确排除。
- **不做 GNN/微调**：与 RAG+Agent 主线无关。
- **不做分布式/高并发**：Streamlit 单进程模型，评测中的"并发测试"仅做轻量验证。

## 2. 技术栈选型

### 2.1 选型总表

| 层次 | 选型 | 版本约束 | 理由 |
|---|---|---|---|
| 语言 | Python | ≥ 3.10（实测 3.12.7） | 生态最全 |
| 生成模型 | DeepSeek `deepseek-chat` | OpenAI 兼容 API | 中文强、成本低、国内直连无需代理 |
| 向量化 | SiliconFlow `BAAI/bge-m3` | 1024 维 / 8192 token 上限 | 零本地部署；长上下文适合整章切块 |
| 重排序 | SiliconFlow `BAAI/bge-reranker-v2-m3` | 交叉编码器 | 零本地部署；支持 `top_n` 与长文档分片打分 |
| 关键词检索 | `rank_bm25` | 纯 Python | 无需额外服务，索引可 pickle 持久化 |
| 向量数据库 | ChromaDB | 持久化模式 | 轻量、嵌入式、支持 metadata 过滤与增量 upsert |
| PDF 解析 | **PyMuPDF (fitz)** | | 抽取速度与准确率均优于 PyPDF2 / pdfplumber（见 §5.1.1 实测） |
| DOCX 解析 | `python-docx` | | 事实标准 |
| 前端 | Streamlit | | 三栏布局 + 流式输出开箱即用 |
| 配置管理 | `pydantic-settings` | | 类型安全 + `.env` 自动加载 + 校验 |
| HTTP | `httpx` | | 支持超时/重试/连接池；`openai` SDK 底层依赖 |
| 数据处理 | `pandas` / `matplotlib` | | 评测报表与图表 |
| 测试 | `pytest` | | 核心算法单测 |

### 2.2 被否方案与理由

| 方案 | 否决理由 |
|---|---|
| LangChain / LlamaIndex 作为主框架 | 作业明确要求手写 ReAct 循环与 RRF 融合；框架的 `AgentExecutor` 会把这些逻辑藏在黑盒里，违背教学目标。且依赖层厚重、版本迭代破坏性强 |
| 本地 `sentence-transformers` 跑 bge 系列 | 与"不要求本地部署"直接冲突；需下载数 GB 权重并常驻内存 |
| FAISS 替代 Chroma | FAISS 性能更好但**不支持 metadata 存储与原地更新**，增量索引需自行维护 ID↔向量的映射表，工程量与收益不成比例 |
| Gradio 替代 Streamlit | 三栏自定义布局 Gradio 实现更繁琐；Streamlit 的 `st.chat_message` / `st.status` 天然适配对话+轨迹场景 |
| 只用向量检索（朴素 RAG） | 学术术语（如 `BatchNorm`、`mIoU`）靠语义向量易被泛化稀释，必须有关键词通道兜底 |
| 只做关键词检索 | 无法处理"这篇论文怎么解决过拟合"↔"正则化策略"这类语义等价表达 |

### 3.2 两条核心数据流

**数据流 A：入库（离线）**

```
文件 → loaders.load_document() → Document(pages[])
     → chunkers.split() → List[Chunk]
     → embeddings.embed_batch() → List[float[1024]]
     → vectorstore.upsert()  (Chroma)
     → bm25_index.add()      (pickle)
```

**数据流 B：问答（在线）**

```
用户问题
  → memory.build_context(session_id)
  → router.classify(question)        # 判断是否需要检索
  → [需要] kb_search tool
        → hybrid.search(mode=hybrid_rerank)
              ├─ vector_search(top=20)  ┐
              └─ bm25_search(top=20)    ├─ RRF 融合 → top=20
                                        ┘
              └─ rerank(query, 20) → top=5
  → prompts.build_rag_prompt(question, chunks)
  → llm.stream_chat()  → 流式 token
  → rag.attach_citations()  → [1][2] 映射回 文档名+页码
  → memory.append(session_id, turn)
  → trace.record(AgentStep...) → 前端轨迹树
```

### 3.3 模块依赖方向（单向，无环）

```
ui  →  agent  →  generation  →  retrieval  →  ingest  →  core
                     ↓              ↓            ↓
                 observability  (横切所有层，只被依赖不被反向依赖)
```

**关键约束**：下层永远不 import 上层。`retrieval` 不知道 `agent` 存在。这样每一层都可独立测试，且可独立替换（例如换 Embedding 供应商只改 `core/providers.py`）。

## 5. 五大模块构建方案

### 模块一：文档处理与检索层

**目标**：构建数据底座——把异构学术文档转成可精确检索的向量+关键词双索引。

#### 5.1.1 多格式文档加载器（`ingest/loaders.py`）

**统一输出结构**（定义在 `core/schemas.py`）：

```python
@dataclass
class Page:
    text: str
    page_no: int          # 1-based，用于引用溯源

@dataclass
class Document:
    doc_id: str           # sha256(文件内容)[:16]，内容寻址
    filename: str
    filetype: str         # pdf | docx | txt | md
    pages: list[Page]
    meta: dict            # 标题/作者/年份/DOI（尽力抽取）
    ingested_at: str
```

**设计要点**：

- **内容寻址的 `doc_id`**：用文件内容的 sha256 前 16 位作为 ID。同一文件重复上传会得到相同 ID，因此**天然幂等**——这是增量索引"跳过未变更文件"的基础。
- **PyMuPDF 逐页抽取**：`page.get_text("text")`，天然保留页码，满足引用溯源需求。
- **三种 PDF 方案的对比实验**（作业要求）：

| 方案 | 速度 | 双栏排版 | 表格 | 结论 |
|---|---|---|---|---|
| PyPDF2 | 快 | 差（常串行） | 不支持 | 淘汰：双栏论文串行严重 |
| pdfplumber | 慢（3-5x） | 中 | **好** | 备选：仅在需抽表格时启用 |
| **PyMuPDF** | **快** | **好**（按块坐标排序） | 中 | **采用**：学术论文以正文为主，速度与排版兼顾 |

- **失败重试**：`pipeline.py` 中对每个文件做 3 次指数退避重试，失败记录进 `IngestReport` 而非中断整批。

**验收**：对同一份双栏 IEEE 论文，PyMuPDF 抽出的正文段落顺序正确、无左右栏交错。

#### 5.1.2 文本分块策略（`ingest/chunkers.py`）

统一接口：

```python
class BaseChunker(ABC):
    @abstractmethod
    def split(self, doc: Document) -> list[Chunk]: ...
```

`Chunk` 结构：

```python
@dataclass
class Chunk:
    chunk_id: str         # f"{doc_id}::{page_no}::{seq}"
    doc_id: str
    filename: str
    page_no: int          # ★ 引用溯源的关键字段
    seq: int
    text: str
    token_count: int      # 估算
```

**三种策略**：

| 策略 | 实现 | 适用 |
|---|---|---|
| `fixed` | 按估算 token 数硬切，`chunk_size` 可配 256/512/1024，`overlap` 默认 15% | 基线对照 |
| `recursive` | 按 `["\n\n", "\n", "。", ". ", " "]` 分隔符优先级递归降级，尽量在自然边界断开 | **默认策略** |
| `semantic` | 先按段落聚簇，计算相邻句向量余弦相似度，低于阈值处切分 | 追求检索精度 |

**学术文本特化处理**：

- **页眉页脚剔除**：对同一文档所有页做行频统计，出现在 >60% 页面的短行判为页眉页脚。
- **跨页段落合并**：若某 chunk 结尾无终止标点且下一页首块开头为小写字母，则合并。
- **公式与参考文献**：`References`/`参考文献` 标题之后的内容打 `is_reference=True` 标记，检索时默认降权（参考文献列表对问答价值低但极易命中关键词）。

**对比实验设计**：固定评测集不变，只切换分块策略与 `chunk_size`，记录 Hit@5 / MRR，产出《分块策略对比实验报告》。

#### 5.1.3 向量化与向量库（`core/providers.py` + `retrieval/vectorstore.py`）

**SiliconFlow Embedding 客户端**：

```python
POST https://api.siliconflow.cn/v1/embeddings
{
  "model": "BAAI/bge-m3",
  "input": ["文本1", "文本2", ...],   # 批量，默认 32 条/批
  "encoding_format": "float"
}
→ {"data": [{"embedding": [...1024], "index": 0}, ...],
   "usage": {"prompt_tokens": N, "total_tokens": N}}
```

**关键工程点**：

1. **分批**：单请求最多 32 条（`EMBED_BATCH_SIZE`），避免超限。
2. **本地缓存**：以 `sha256(text)` 为 key 缓存向量到磁盘。重复文本（如 chunk overlap 部分）不重复计费。**这是成本控制的关键**。
3. **指数退避重试**：429/5xx 重试 3 次，间隔 1s/2s/4s。
4. **失败降级**：单批失败不放弃整篇文档，记录失败 chunk 并在报告中列出。

**Chroma 封装**：

```python
class VectorStore:
    def upsert(self, chunks, embeddings) -> None      # 幂等，同 ID 覆盖
    def delete_document(self, doc_id) -> int
    def query(self, query_vec, top_k, where=None) -> list[ScoredChunk]
    def list_documents(self) -> list[DocStatus]        # 供前端文档面板
```

**增量更新策略**：`upsert` 前先查该 `doc_id` 是否已存在且内容哈希未变；未变则**整篇跳过**，只有新文件或变更文件才重新向量化。满足作业"新文档加入时无需重建全量索引"的要求。

#### 5.1.4 混合检索与重排序（`retrieval/fusion.py` + `hybrid.py`）

**BM25 通道**（`bm25_index.py`）：

- 用 `rank_bm25.BM25Okapi`，语料为全部 chunk 的文本。
- **中文分词**：`jieba` 不在依赖里，改用「字符二元组（bigram）+ 英文单词」的轻量分词，对中文学术文本召回效果可接受且零依赖。英文部分按 `\b[a-zA-Z0-9\-]+\b` 抽词并转小写。
- 索引与 chunk 元数据一起 pickle 到 `storage/bm25/`，进程重启不需重建。

**RRF 融合**（**手写，作业硬性要求**）：

```python
def rrf_fuse(result_lists: list[list[ScoredChunk]], k: int = 60,
             weights: list[float] | None = None) -> list[ScoredChunk]:
    """倒数排名融合。
    score(d) = Σ_i  w_i / (k + rank_i(d))
    只依赖排名不依赖原始分数量纲，因此无需归一化即可融合
    余弦相似度与 BM25 分数这两种不可比的量。
    """
```

**为什么用 RRF 而不是分数加权求和**：BM25 分数无上界（随语料规模变化），余弦相似度在 [-1,1]。直接加权需先做归一化，而归一化方式（min-max / z-score）会引入额外超参且对异常值敏感。RRF 只用排名，天然免调参、免归一化——这是它在工业界混合检索中被广泛采用的原因。

**重排序**（`reranker.py`）：

```python
POST https://api.siliconflow.cn/v1/rerank
{
  "model": "BAAI/bge-reranker-v2-m3",
  "query": "用户问题",
  "documents": ["候选chunk文本", ...],   # 通常 20 条
  "top_n": 5,
  "return_documents": false
}
→ {"results": [{"index": 3, "relevance_score": 0.87}, ...]}
```

`return_documents=false` 以减小响应体，文本我们本地已有（靠 `index` 回查）。

**三档检索编排**（`hybrid.py`）：

```python
class HybridRetriever:
    def search(self, query: str, mode: str = "hybrid_rerank",
               top_k: int = 5) -> RetrievalResult:
        # mode ∈ {"vector", "hybrid", "hybrid_rerank"}
```

| 档位 | 流程 | 用途 |
|---|---|---|
| `vector` | 向量 top-20 → 截断 top-5 | 朴素 RAG 基线 |
| `hybrid` | 向量 top-20 + BM25 top-20 → RRF → top-5 | 验证关键词通道增益 |

### 模块二：RAG 生成层

**目标**：在检索层之上构建带引用溯源、流式输出的高质量问答。

#### 5.2.1 Prompt 工程（`generation/prompts.py`）

**RAG 主 Prompt 结构**（四段式）：

```
[系统角色]
你是严谨的科研助理。你只能依据"参考资料"回答，不得编造。

[参考资料]
[1] (来源: attention_is_all_you_need.pdf 第3页)

[2] (来源: bert.pdf 第7页)
<片段正文>

[用户问题]
<question>

[输出要求]
1. 每个事实性陈述后必须紧跟引用标记，格式 [1] 或 [1][2]
2. 引用编号必须对应上方参考资料的编号，不得虚构
```

**上下文拼接策略**：

1. **按相关性降序排列**——LLM 对上下文开头和结尾的注意力更强（"lost in the middle"），因此最高分片段放最前。
2. **Token 预算动态截断**——`MAX_CONTEXT_TOKENS` 默认 3000。逐条累加，超预算即停止；若某条会超预算但剩余空间 > 200 token，则截断该条而非丢弃。
3. **来源标注内联**——编号在拼接时即固定，生成后无需二次匹配。

**生成参数对照实验**：固定问题集，扫 `temperature ∈ {0, 0.3, 0.7}` × `top_p ∈ {0.8, 0.95}`，人工评分正确性/完整性/引用准确性，产出 Prompt 实验记录。

#### 5.2.2 流式输出（`generation/rag.py`）

DeepSeek 使用 OpenAI 兼容的 SSE 流：


#### 5.2.4 降级策略（`generation/fallback.py`）

| 触发条件 | 降级行为 | 用户可见提示 |
|---|---|---|
| 检索 0 命中 | 退到纯 LLM 生成 | ⚠️ "知识库中未找到相关文档，以下回答来自模型自身知识，请谨慎参考" |
| Rerank 最高分 < `MIN_RELEVANCE`（默认 0.2） | 仍生成，但标注低置信 | ⚠️ "检索置信度较低，请确认以下片段是否相关"+ 展示候选片段供用户确认 |
| Embedding API 失败 | 退到纯 BM25 检索 | ℹ️ "向量服务暂不可用，已降级为关键词检索" |
| LLM API 失败（重试后） | 返回错误卡片 | ❌ "模型服务暂时不可用，请稍后重试"+ 重试按钮 |
| 上下文超长 | 按 §5.2.1 动态截断 | 无提示（静默处理） |

**设计原则**：**任何一条链路故障都不能让整个请求 500**。每一层都要有"退一步仍可用"的路径。

### 模块三：Agent 决策层

**目标**：构建具备自主推理、多工具调用、记忆管理能力的决策中枢。

#### 5.3.1 ReAct 核心循环（`agent/react.py`）

**作业明确要求手写，约 200 行，不使用 LangChain。**

**文本协议**（不依赖 function calling，兼容性更好且轨迹可读）：

```
Thought: 我需要先查知识库里关于 BERT 微调策略的内容
Action: kb_search
Action Input: {"query": "BERT 微调 策略", "top_k": 5}
Observation: [1] (bert.pdf 第7页) 我们使用了 AdamW ...

Thought: 已有充分信息，可以回答
Action: Finish
Action Input: {"answer": "根据知识库，BERT 微调使用 AdamW 优化器 [1] ..."}
```

**循环骨架**：

```python
class ReActAgent:
    def run(self, question: str, session_id: str) -> AgentResult:
        steps: list[AgentStep] = []
        scratchpad = ""
        for i in range(self.max_iterations):        # 默认 6
            prompt = self._build_prompt(question, scratchpad)
            raw = self.llm.complete(prompt, stop=["Observation:"])
            thought, action, action_input = self._parse(raw)

            steps.append(AgentStep(index=i, thought=thought,
                                   action=action, action_input=action_input))

            if action == "Finish":                  # 终止条件 1
                return AgentResult(answer=action_input["answer"], steps=steps)

            if self._is_loop(steps):                # 终止条件 2：重复调用
                steps.append(AgentStep(note="检测到重复调用，强制收敛"))
                return self._force_conclude(question, steps)

            obs = self.executor.run(action, action_input)   # 超时/重试/并行
            steps[-1].observation = obs
            scratchpad += f"\nThought: {thought}\nAction: {action}\nAction Input: {...}\nObservation: {obs}\n"

        return self._force_conclude(question, steps)  # 终止条件 3：轮次耗尽
```

**三个终止条件**（防止死循环）：

1. 显式 `Finish`；
2. **重复调用检测**——同一 `(action, hash(action_input))` 出现第 2 次即判定陷入循环；
3. **轮次上限**——`max_iterations=6` 耗尽后调 `_force_conclude`，用现有 scratchpad 让 LLM 直接作答。

**System Prompt 结构**（三段式）：

```
[角色定义] 你是科研助理 Agent，通过"思考-行动-观察"循环解决问题。
[可用工具] <每个工具的名称、功能、参数 JSON Schema、使用时机>
[输出格式约束] 必须严格按 Thought/Action/Action Input 格式；每次只能一个 Action；
              信息足够时必须用 Finish 结束，不要无谓地反复检索。
```

#### 5.3.2 工具集（8 个，`agent/tools/`）

**工具抽象**：

```python
@dataclass
class Tool:
    name: str
    description: str
    parameters: dict          # JSON Schema
    func: Callable[..., str]
    timeout_s: float = 30.0
```

**注册表**：`tools/__init__.py` 用装饰器 `@register_tool` 自动收集，`build_registry()` 返回 `dict[str, Tool]`。新增工具只需加文件加装饰器，不改动 `react.py`。

| # | 工具名 | 功能 | 关键参数 |
|---|---|---|---|
| 1 | `kb_search` | **核心工具**，封装模块二 RAG 引擎检索 | `query`, `top_k`, `mode` |
| 2 | `paper_meta` | 抽取论文标题/作者/年份/DOI/摘要 | `doc_id` 或 `filename` |
| 3 | `paper_compare` | 对比两篇论文的方法/数据集/结果 | `doc_id_a`, `doc_id_b`, `aspect` |
| 4 | `extract_keywords` | 从问题或文档抽核心关键词 | `text`, `top_n` |
| 5 | `summarize_paper` | 生成结构化摘要（背景-方法-结果-结论） | `doc_id` |
| 6 | `calculator` | 数学计算（`eval` 白名单 AST 安全求值） | `expression` |
| 7 | `current_time` | 返回当前时间 | 无 |
| 8 | `web_search` | 联网搜索（DuckDuckGo HTML 端点，可选） | `query`, `max_results` |

**安全要点**：`calculator` 绝不用裸 `eval`。用 `ast.parse(expr, mode="eval")` 遍历 AST，白名单放行 `BinOp/Num/UnaryOp/Constant/Pow` 等节点，拒绝 `Call/Attribute/Name`，从而杜绝 `__import__('os').system(...)` 类注入。

#### 5.3.3 决策优化

**（a）工具选择路由**（`router.py`）

先用零成本的规则预判，命中则直接短路，避免为简单问题付出完整 ReAct 的 token 代价：

| 问题特征 | 路由 | 节省 |
|---|---|---|
| 纯算术表达式（正则全匹配） | 直接调 `calculator`，跳过 LLM 推理 | ~100% |
| 含"现在/今天/当前时间" | 直接调 `current_time` | ~100% |
| 含"对比/区别/相比"+ 两个已知论文名 | 直接调 `paper_compare` | 省 1-2 轮 |
| 命中语义缓存 | 直接返回缓存答案 | ~100% |
| 其余 | 进入完整 ReAct 循环 | — |

规则未命中时可选用一次轻量 LLM 分类（`ROUTER_USE_LLM=true`），但默认关闭以省 token。

**（b）并行工具调用**（`executor.py`）

当 LLM 在单个 Action 中请求多个独立调用时（`Action: parallel` + 调用列表），用 `ThreadPoolExecutor(max_workers=4)` 并发执行：

```python
with ThreadPoolExecutor(max_workers=4) as pool:
    futures = {pool.submit(self._run_one, c): c for c in calls}
    for f in as_completed(futures, timeout=self.parallel_timeout):
        ...
```

**并行安全性**：只允许并行**只读**工具（`kb_search`/`paper_meta`/`web_search` 等）；任何有副作用的工具强制串行。

**（c）错误恢复**（`executor.py`）

| 故障 | 处理 |
|---|---|
| 工具超时（默认 30s） | 重试 1 次；再失败则返回 `"工具 {name} 超时，请尝试其他方式或直接回答"` 作为 Observation，让 Agent 自行绕路 |
| 工具抛异常 | 捕获，返回结构化错误描述作为 Observation（**不中断循环**），Agent 可换工具 |
| JSON 参数解析失败 | 尝试正则修复引号；仍失败则提示 Agent 重新生成 Action Input |
| 重复调用 | 由 `react.py` 的循环检测终止 |
| LLM 连续 3 次输出格式非法 | 强制 `Finish`，用兜底 prompt 直接生成答案 |

**注意**：工具的错误**必须作为 Observation 交还给 Agent**，而不是直接抛给用户。这正是 ReAct 自愈能力的关键——Agent 看到错误后能自行换策略。

#### 5.3.4 多轮对话记忆（`agent/memory.py`）

```python
@dataclass
class Turn:
    role: str          # user | assistant
    content: str
    ts: str
    cited_chunk_ids: list[str] = field(default_factory=list)

class ConversationMemory:
    def __init__(self, max_tokens=2000, summarize_after_turns=8): ...
    def get(self, session_id: str) -> list[Turn]
    def append(self, session_id: str, turn: Turn) -> None
    def build_context(self, session_id: str) -> tuple[str, str | None]:
        """→ (近期原文, 早期摘要)"""
```

**三层机制**：

1. **会话隔离**——`dict[session_id, list[Turn]]`，前端每次新建会话生成新 UUID。
2. **滑动窗口 Token 控制**——从最新往旧累加 token，超 `max_tokens` 即截断。**整轮保留**（不切断 user/assistant 配对），避免产生语义残缺的历史。
3. **摘要压缩**——当轮次 > `summarize_after_turns` 时，把最早的一半轮次交给 LLM 压缩成一段 200 字以内的阶段性摘要，用摘要替换原始历史。摘要本身在下一次压缩时会被并入新摘要（滚动压缩）。

**持久化**：会话落盘到 `storage/sessions/{session_id}.json`，前端可切换/删除历史会话。

### 模块四：系统集成与前端展示

**目标**：把五大模块整合成可交互 Web 应用，并让 Agent 的决策过程完全透明。

#### 5.4.1 RAG + Agent 深度融合（`agent/tools/kb_search.py`）

RAG 不是与 Agent 并列的模块，而是 Agent 的**一个 Tool**。这个设计带来两个直接好处：

1. **可跳过**——简单问题（算术、寒暄）不触发检索，省 token 省延迟；
2. **可组合**——"对比论文 A 和 B"由 `paper_compare` 内部各调一次 `kb_search` 完成。

**统一数据结构**（`core/schemas.py`）充当模块间的"接口契约"：

```python
@dataclass
class Message:      role: str; content: str; citations: list[Citation] = ...
@dataclass
class Citation:     index: int; filename: str; page_no: int; chunk_id: str; snippet: str
@dataclass
class AgentStep:    index: int; thought: str; action: str; action_input: dict
                    observation: str; latency_ms: int; tokens: int; error: str | None
@dataclass
class AgentResult:  answer: str; citations: list[Citation]; steps: list[AgentStep]
                    tokens: dict; latency_ms: dict; route: str; degraded: str | None
```

所有模块只通过这 5 个结构通信。**改任何一层的内部实现都不影响其他层**——这是"模块化松耦合"的可验证体现。

**路由精细化**：`kb_search` 工具被调用时，Agent 在 System Prompt 中被明确告知：

> 当问题涉及知识库中的具体论文内容、方法、实验数据时，使用 kb_search。
> 当问题是通用常识（如"什么是机器学习"）或当前时间/计算类时，**不要**调用 kb_search。

#### 5.4.2 可观测性（`observability/`）

**`trace.py`**：每个 `AgentStep` 记录完整四元组 + 耗时 + token + 错误。轨迹以 JSONL 追加到 `storage/logs/trace.jsonl`，并把 `AgentResult.steps` 直接返回给前端。

**`metrics.py`** 聚合指标：

| 指标 | 计算方式 |
|---|---|
| 每步 token 消耗 | 按工具分别累计 `tokens` |
| 检索命中率 | 检索返回非空且 top1_score ≥ 阈值的请求数 / 总检索请求数 |
| 响应延迟 | `retrieve` / `rerank` / `generate` / `total` 分别记录 P50/P95 |
| Agent 决策路径 | 直接由 steps 序列构成 |
| 工具调用成功率 | 成功调用数 / 总调用数，按工具分组 |
| 平均推理轮次 | `len(steps)` 均值 |

**健康检查**：`health_check()` 分别探测（a）DeepSeek `/models` 可达性；（b）SiliconFlow embedding 一次 1-token 调用；（c）Chroma 集合可读；（d）BM25 索引文件存在。任一失败在前端顶部显红色横幅。**注意**：探测要快速失败（timeout 5s），不能让健康检查本身拖慢页面。

#### 5.4.3 Streamlit 界面（`streamlit_app.py`）

**三栏布局**：

```python
left, center, right = st.columns([1, 2.4, 1.4])
```

| 面板 | 内容 |
|---|---|
| **左栏 · 文档管理** | `st.file_uploader(accept_multiple_files=True)`；上传后逐文件 `st.progress` 显示向量化进度；文档列表展示 `文件名 / 页数 / chunk 数 / 入库时间`，带删除按钮；"重建索引"按钮 |

**Streamlit 关键实现细节**：

- **`st.session_state` 保存会话状态**：`session_id`、`messages`、`last_result`。Streamlit 每次交互都重跑整个脚本，所有可变状态必须放 session_state，否则对话历史会丢。
- **流式渲染**：用 `st.write_stream()` 消费 `stream_answer()` 生成器，它原生支持打字机效果并返回完整文本。
- **缓存跨用户重跑**：`@st.cache_resource` 装饰 `get_retriever()` / `get_agent()`，避免每次交互都重建 Chroma 连接和 BM25 索引（这是 Streamlit 应用最常见的性能陷阱）。
- **侧栏历史会话管理**：`新建会话` / 切换 / 删除。

#### 5.4.4 端到端联调与测试

**主流程用例**：上传 3 篇 PDF → 等待索引完成 → 问"论文用了什么数据集" → 验证有引用且引用页码正确 → 查看轨迹树。

**边缘用例清单**：

| 场景 | 期望行为 |
|---|---|
| 空知识库提问 | 提示"知识库为空，请先上传文档"，不抛异常 |
| 超大文档（100+ 页） | 分块与向量化分批进行，进度条正常推进 |
| 超长对话（20+ 轮） | 触发摘要压缩，token 不无限增长 |
| API key 错误 | 健康检查红色横幅 + 友好错误，不显示堆栈 |
| 提问纯算术 | 路由到 calculator，轨迹中无 kb_search |
| 检索无命中 | 降级为纯生成 + 明确的"未找到"提示 |
| 同一文件重复上传 | `doc_id` 相同，跳过重建，提示"已存在，已跳过" |

### 模块五：评测与项目交付

**目标**：以数据证明系统有效，产出专业评测报告与全部交付物。

#### 5.5.1 评测集构建（`eval/qa_set.jsonl`）

**方案**：以"Transformer 在计算机视觉中的应用"为研究方向，收集 10-20 篇论文（含经典 ViT、Swin、DETR、MAE 等），构建 50+ 问答对。

**格式**：

```json
{"id":"q001","type":"factual","question":"ViT 在哪个数据集上预训练？",
 "gold_answer":"ImageNet-21k（14M 子集）","gold_chunk_ids":["a1b2c3::3::2"],
 "gold_doc_ids":["a1b2c3"],"difficulty":"easy"}
```

**四类问题配比**（各约 25%）：

| 类型 | 示例 | 考察 |
|---|---|---|
| 事实性 | "这篇论文用了什么数据集？" | 检索精度 |
| 对比性 | "论文 A 和论文 B 的方法有什么区别？" | 多文档检索 + Agent 组合 |
| 归纳性 | "这一方向主流的评估指标有哪些？" | 跨文档聚合 |
| 推理性 | "为什么作者选择 XX 而不是 YY？" | 语义理解 + 生成质量 |

**构建方法**：先由 LLM 基于 chunk 生成候选问答对，**再由人工逐条核对 `gold_answer` 与 `gold_chunk_ids`**。未经人工核对的自动标注会让评测失去意义——这是评测集构建中最容易被偷懒的一步。

#### 5.5.2 系统级性能评估（`scripts/eval_retrieval.py` / `eval_agent.py`）

**检索指标**：

```
Hit@5  = 命中 gold_chunk 的查询数 / 总查询数
MRR    = mean(1 / rank_of_first_relevant)
Recall = 召回的相关 chunk 数 / 全部相关 chunk 数
```

**对比维度**：`mode ∈ {vector, hybrid, hybrid_rerank}` × `chunk_size ∈ {256, 512, 1024}` × `chunk_strategy ∈ {fixed, recursive, semantic}`。输出 CSV + matplotlib 图表到 `eval/reports/`。

**Agent 指标**：工具调用准确率（期望工具 == 实际首个工具）、平均推理轮次、降级触发率。

**端到端指标**：平均/P95 延迟、平均 token 消耗（prompt + completion 分开统计，便于算成本）。

**答案质量**：人工按 1-5 分评正确性、完整性、引用准确性三项，双人评分取均值。

#### 5.5.3 Bad Case 分析与优化

`docs/Bad Case分析报告.md` 中按四类归因：

| 类别 | 归因方向 |
|---|---|
| 检索失败 | 分块过碎/过大？关键词通道未命中？表格或公式丢失？ |
| 生成错误 | 上下文噪声过多？Prompt 约束不足？温度过高？ |
| 引用错误 | 编号映射错位？模型虚构编号？（在 `attach_citations` 中做编号合法性校验，非法编号标注为"未验证引用"） |
| Agent 决策错误 | 路由误判？工具描述不清？陷入无效循环？ |

**要求**：每类给出根因 + 改进方案，并**至少实施一轮迭代优化，记录优化前后对比数据**。

## 7. 风险与应对

| 风险 | 可能性 | 影响 | 应对 |
|---|---|---|---|
| 用户无 API key，无法端到端验证 | **高** | 高 | **Mock Provider**：确定性伪向量 + 固定话术 LLM，跑通全链路与评测脚本；交付后改一行 `.env` 切换 |
| SiliconFlow 免费额度耗尽/限流 | 中 | 中 | 磁盘缓存向量（同文本不重复调用）+ Rerank 可关闭（`hybrid` 档仍可用）+ 明确限流错误提示 |
| 多进程重复计费 | 低 | 低 | Chroma 检索仅需 query embedding（1 次调用），文档向量有缓存 |
| Chroma 与 Python 3.12 兼容问题 | 低 | 中 | 优先 `>=0.5.0`；若失败，提供 numpy 内存索引的兜底实现（接口一致，`vectorstore.py` 内切换） |
| 流式模式下拿不到 token 统计 | 中 | 低 | 显式传 `stream_options={"include_usage": True}` |
| Windows 路径与中文文件名 | 中 | 中 | 全部用 `pathlib.Path`；文件名入库前做安全化处理，展示名与磁盘名分离 |
| Streamlit 重跑导致状态丢失 | **高** | 中 | 所有可变状态放入 `st.session_state`；重资源用 `@st.cache_resource` |
| 评测集人工标注耗时 | 中 | 中 | LLM 生成候选 + 人工核对，先做 20 条跑通流程再扩充到 50+ |
