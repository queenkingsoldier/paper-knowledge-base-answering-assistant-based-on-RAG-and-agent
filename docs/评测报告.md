## 0. 重要前提：本次评测运行在 Mock 模式下

本机环境**没有配置任何真实 API Key**，因此本次全部数字由 **Mock Provider** 产生：

| 组件 | 本次评测使用的实现 | 与真实的差距 |
|---|---|---|
| 生成 LLM | `MockLLM`（固定话术） | 答案内容无意义，仅验证链路 |
| 向量化 | `MockEmbedding`（sha256 播种的确定性伪向量） | **语义能力为零**：语义相近的文本并不相邻 |
| 重排序 | `MockRerank`（词元重合度打分） | 不是交叉编码器，信息量低于 RRF |

**因此本报告的定位是**：证明评测工具链本身是正确且可复现的，给出检索架构的**下界结论**，并明确列出哪些结论必须在真实 API 下复核。

**不能**把本报告的数字当作系统真实性能。

## 2. 检索层评测

### 2.1 片段级口径（gold_chunk_ids，精确到段）

| 档位 | Hit@1 | Hit@3 | Hit@5 | Recall@1 | Recall@3 | Recall@5 | MRR |
|---|---|---|---|---|---|---|---|
| `vector` | 0.25 | 0.60 | 0.85 | 0.200 | 0.395 | 0.565 | 0.4633 |
| `hybrid` | **0.65** | **1.00** | **1.00** | **0.410** | **0.895** | **0.965** | **0.8167** |
| `hybrid_rerank` | **0.65** | 0.95 | **1.00** | **0.410** | 0.880 | 0.950 | 0.7933 |

### 2.2 文档级口径（gold_doc_ids，与分块方式无关）

| 档位 | Hit@1 | Hit@3 | Hit@5 | Recall@5 | MRR |
|---|---|---|---|---|---|
| `vector` | 0.30 | 0.85 | 0.90 | 0.850 | 0.5542 |
| `hybrid` | 0.85 | 1.00 | 1.00 | 0.975 | 0.9167 |
| `hybrid_rerank` | **0.95** | **1.00** | **1.00** | **0.975** | **0.9667** |

### 2.3 结论

**结论 1（可靠）：混合检索相对朴素向量检索有大幅提升。**

| 口径 | vector MRR | hybrid MRR | 相对提升 |
|---|---|---|---|
| 片段级 | 0.4633 | 0.8167 | **+76%** |
| 文档级 | 0.5542 | 0.9167 | **+65%** |

在五种不同分块配置下（见《分块策略对比实验报告》表 1）该提升稳定复现（+33% ~ +64%），无一例外。**混合检索的架构选择得到实验支持。**

**结论 2（可信度中等）：重排序在片段级反而有害，但这是 Mock 打分器的缺陷，不是架构缺陷。**

片段级 MRR：`hybrid` 0.8167 → `hybrid_rerank` 0.7933（下降）；Hit@3：1.00 → 0.95（下降）。
文档级 MRR：`hybrid` 0.9167 → `hybrid_rerank` 0.9667（提升）。

矛盾的解释：`MockRerank` 只看单路词元重合，**信息量低于 RRF**（RRF 融合了向量与 BM25 两路）。用一个信息量更少的打分器去重排一个信息量更多的排序，结果自然更差——在需要精确到段的片段级口径上，这种损失会直接暴露。

真实 `bge-reranker-v2-m3` 是交叉编码器，对 (query, passage) 联合编码，信息量严格多于任何单路分数。**但这必须先验证，不能假设**（见 §5 待办）。

**结论 3：降级率 0.0。** 全部 20 条检索请求在三种档位下都正常返回，没有触发任何降级路径。

## 3. Agent 决策层评测

| 指标 | 值 | 说明 |
|---|---|---|
| 工具调用准确率 | **1.0000**（22/22） | 与 `expected_tool` 完全一致 |
| 平均推理轮次 | 1.909 | 最大 2 轮 |
| 崩溃率 | 0.0000 | 无一次异常穿出 |
| 降级率 | 0.0000 | 无一次非正常终止 |
| 平均延迟 | 6 ms | **Mock 模式，无参考价值** |
| P95 延迟 | 8 ms | 同上 |
| Prompt token 总量 | 40,003 | 22 条合计 |
| Completion token 总量 | 1,706 | 22 条合计 |

### 3.1 一次真实的修复：路由未接入 Agent 路径

首次评测时工具准确率为 **0.9091（20/22）**，两条工具类问题被误判：

| 问题 | 期望工具 | 实际工具 |
|---|---|---|
| `3.14 乘以 2.56 等于多少？` | `calculator` | `kb_search` |
| `现在是几点？` | `current_time` | `kb_search` |

**根因**：`agent/router.py` 的规则路由已实现，但**从未被 `ReActAgent.run()` 调用**——只有前端 `answer_once` 用它做过空库判断。纯算术问题因此照走完整 ReAct 循环，触发检索。

**修复**：在 `ReActAgent.run()` 入口接入 `_direct_route()`，命中 `direct_tool` 时直接执行工具并返回，跳过整个循环。

**修复后**：准确率 0.9091 → **1.0000**；Prompt token 44,055 → 40,003（**下降 9.2%**）。第二条收益正对应构建书 §5.3.3「减少无效推理轮次」。

### 3.2 一处中文口语的修复

`3.14 乘以 2.56 等于多少？` 仍被判为 `agent`。原因是路由的算式抽取正则只认 `+ - * /` 符号，而中文用户习惯写「乘以」。

构建书 §5.3.1 举的例子恰好就是「3.14乘以2.56」，所以这是必须支持的主路径，不是边缘情况。修复方式：抽算式前先把中文运算符词（乘以/除以/加上/减去…）归一化成符号。

修复后 `3.14 乘以 2.56 等于多少？` → `calculator`，准确率达到 1.0。同时保持「纯数字不误判」的约束不变（`"3.14"` → `agent`，`"论文1和论文2的区别"` → `agent`）。

## 7. 复现命令

```bash
# 1) 建索引（与评测集 gold 对齐的配置）
python scripts/build_index.py eval/demo_corpus --strategy recursive --chunk-size 200 --rebuild

# 2) 校验评测集标注
python scripts/validate_qa_set.py eval/qa_set_demo.jsonl

# 3) 检索评测（两个口径）
python scripts/eval_retrieval.py --qa eval/qa_set_demo.jsonl --gold-level chunk --modes vector hybrid hybrid_rerank --ks 1 3 5
python scripts/eval_retrieval.py --qa eval/qa_set_demo.jsonl --gold-level doc   --modes vector hybrid hybrid_rerank --ks 1 3 5

# 4) Agent 评测
python scripts/eval_agent.py --qa eval/qa_set_demo.jsonl

# 5) 全链路自检
python scripts/smoke_test.py

# 6) 单元测试
python -m pytest tests/
```
